# prompts/ — Prompt 迭代复测模块

> 基于评测结果迭代结构化输出 Prompt（补背景 → 明格式 → 加约束），20 条任务 × 4 版模板实测格式合规率，沉淀可复用模板。

## 背景

结构化输出（信息抽取/意图分类/文本改写）直接用朴素指令调用大模型时，常见失效：输出夹带解释文字无法程序化解析、字段缺失、信息不全时编造。本模块用**同一题集、四个模板版本**实测每次迭代带来的合规率变化，让"Prompt 调优"从感觉变成数据。

## 模板演进（templates/，git 历史一次 commit 一版，演进可回溯）

| 版本 | 迭代动作 | 针对问题 |
| --- | --- | --- |
| `baseline.txt` | 朴素指令 | 对照组，暴露全部问题 |
| `v2_加背景.txt` | 补充角色与业务背景 | 模型不懂招聘域语境 |
| `v3_加格式约束.txt` | 只输出 JSON + 字段清单 | 输出夹带解释/代码块，无法解析 |
| `v4_加边界约束.txt` | null 兜底 / 日期薪资格式 / 矛盾标注 | 信息缺失时编造、格式不统一 |

## 任务集（data/test_cases.csv，20 条）

- **信息抽取 8 条**：岗位 JD、请假单、入职材料、薪资通知、培训通知、简历、调岗公告；
- **意图分类 6 条**：员工咨询问题 → 4 类意图（与 dataset 模块同口径），field_spec 内嵌类别约束；
- **文本改写 6 条**：口语化提问 → 规范表述。

CSV 列：`case_id, task_type, input_text, json_fields（合规校验用目标字段）, field_spec（模板渲染用字段说明）`。

## 合规判定（自动，规则透明）

- **compliance = 1** ⇔ 输出可提取出合法 JSON 对象 **且** `json_fields` 全部字段齐全；
- 分类任务额外记录 `value_valid`（"意图"值是否在给定 4 类之内）；
- 判定代码在 `run_prompt_eval.py::judge_output`，规则即代码，可复查。

## 复现步骤

```bash
# 1. 配置有效 Key（需 Python 3.8+，zhipuai SDK 依赖 typing.Literal）
set ZHIPUAI_API_KEY=你的智谱Key

# 2. 执行复测：20 题 × 4 版 = 80 次调用（内置冒烟检查，Key 无效会提前报错退出）
python prompts/run_prompt_eval.py

# 3. 生成对比报告与图表
python prompts/analyze_prompt_eval.py
```

> 无 Key 时可 `python prompts/run_prompt_eval.py --dry-run` 生成待跑清单；
> 结果文件为 pending 状态时 `analyze_prompt_eval.py` 会拒绝分析并提示，**报告数字全部来自真实调用结果，无预填/虚构**。

## 结果速览

见 `reports/prompt_iter_report.md`（需真实运行后生成）：各版本合规率对比表、分任务类型下钻、baseline→v4 典型改善 case 前后对照、迭代方法论结论。

## 方法论沉淀（可复用）

1. **先补背景**：让模型进入业务语境（角色 + 数据来源说明），再谈格式；
2. **再明格式**："只输出 JSON + 字段清单"一句解决可解析性，是合规率增益最大的一步（见报告数据）；
3. **最后加约束**：null 兜底、格式规范、矛盾标注等边界规则，处理真实脏文本；
4. 每步只加一类约束，合规率变化才能归因到具体动作——这也是本模块分 4 版模板、4 次 git commit 的原因。

## 局限（如实声明）

- 每版本每题单次采样，未做多次采样取多数（正式评估建议 3 次取多数）；
- 合规判定只覆盖"可解析 + 字段齐全"，字段值内容正确性需人工抽检；
- 任务 20 条、单模型（GLM-4-Flash），结论不外推其他模型；
- 沙箱/本地环境 Key 失效时模块处于 dry-run 状态，报告需配置有效 Key 后重跑生成。
